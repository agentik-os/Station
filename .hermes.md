# Station project context

## Ownership and trust boundaries

Station owns the portable AGK platform, release overlays, lifecycle, evidence, recovery, and rollback. Hermes remains the profile-local runtime; AGK-TUI owns RMUX/session UX. Operator, Agentik, Mission, and Private are peer Directors for reversible A0–A3 work. Preserve Linux-home, profile, client, and credential boundaries. Operator may perform bounded host/root mechanics without creating another approval round-trip.

Owner gates remain mandatory for reusable secret/OAuth entry, new spend, legal or binding commitments, publication as Gareth, irreversible deletion, production cutover, and new external access. Discord applications and OAuth authorization remain owner-controlled.

NEVER include API keys, tokens, passwords, secrets, credentials, private keys, or connection strings in reports, logs, commits, prompts, or evidence; replace any accidental occurrence with `[REDACTED]`.

## Memory, context, and Skills

- SOUL defines the agent identity and communication style.
- USER holds stable owner facts and preferences.
- MEMORY holds compact, durable environment facts and lessons.
- This file holds Station project rules, architecture, commands, and boundaries.
- Skills hold repeatable procedures. Do not put procedures or completed-work logs in memory.
- Session history and CompletionStore hold temporary progress and completed mission state.

## Repository workflow

Use a dedicated git worktree and branch for isolated changes. Never overwrite unrelated dirty work. Trace canonical source, installed overlays, bootstrap mirrors, and runtime ownership before editing. New behavior requires a failing test first, the smallest complete implementation, affected tests, syntax/static checks, and an independent review.

Primary verification commands:

```bash
uvx --from pytest --with pyyaml pytest -q tests/
git diff --check
python3 -m py_compile overlay/scripts/*.py
```

Run narrower tests during TDD, then the authoritative affected suite. A pre-existing unrelated failure must be reproduced against the parent revision before it is classified as unrelated.

## Verification and completion

Every non-trivial mission must define observable requirements, artifacts, PASS evidence, stop conditions, and rollback before operational work. Reporting, underlying runtime state, and the canonical CompletionStore gate are separate layers. Completion requires requirement-bound evidence and a passing Completion Oracle; never infer deployment, delivery, or live behavior from source files or a successful mutation receipt alone.

For recurring work, require artifact identity, deterministic checks, coverage gaps, delivery readback, state-commit rules, and pause/rollback procedures.

## Fresh-session acceptance

Before enabling cron, automation, or an OS release, run the deployed workflow in a new Hermes session with no dependency on the originating conversation. The receipt must bind the loaded project-context hash, Skills, toolsets, artifact hash, deterministic checks, delivery state, and rollback procedure. Validate it with the Station durability gate.

## Deployment and rollback

Prefer recoverable, atomic deployment with a pre-change backup and manifest. Use safe drain controllers for gateways and verify the exact runtime transport after reload. Do not restart unrelated gateways. Production cutover remains an owner gate. For project editing, use opt-in Hermes checkpoints plus git worktrees; for runtime/system changes, retain explicit backups and rollback receipts.

## Durable-system rules

A permanent profile is justified only by separate long-lived identity, configuration, credentials, memory, sessions, schedules, or operating lifecycle. Temporary independent work belongs in delegation, a worker lane, a Skill, or a program. Profile audits are metadata-only and never delete or copy profile-private state. Cron retirement and memory rewrites are proposal-only until reviewed.
